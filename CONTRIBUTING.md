# Contributing

## SemVer

OpenADR 3 has adopted the SemVer (https://semver.org) method for labeling incremental releases of the specification and related material. In this model, every release is labeled as major.minor.patch, e.g. 3.0.1. We do not anticipate a major version 4, so the scope of our discussion here is on 3.x.y versions.

A minor release represents significant new features or set of improvements, a patch represents a set of bug fixes or minor improvements.

## Releases

We use the term ‘specification and related material’ to indicate that there is a cluster of artifacts that usually have to be incremented together. The ‘specification’ is most precisely embodied in an openapi YAML document, e.g. `3.0.1/openadr3.yaml`. Whenever this document is modified, there must typically be corresponding updates to the [VTN Reference Implementation (RI)][ri] and the Test Tool, and perhaps to the Definitions or User Guide documents.

Note that the RI, tests, and documents might undergo incremental changes that are not reflected in other artifacts.

A single release may contain multiple incremental changes to one or more artifacts in one or more repos, i.e. a patch revision may contain several changes to a given artifact (file) and to several artifacts in several repos.

Part of our challenge is to maintain release integrity amongst artifacts in multiple GitHub repos via tags, folders, or other mechanisms.

## Definition of a Release

The profile Working Group (pWG) guiding the maintenance of the specification will sort known ‘requirements’ into a set of one or more upcoming releases. New ‘requirements’ may be included in the upcoming release or assigned to a future release. In general there will be 3 releases in scope at a given time:

- the most recently ‘locked’, i.e labelled, release (which may require a patch),

- the next upcoming release (most activity will be focused here),

- the ‘next next’ release (which will include issues that are not pressing enough or require too many resources to address in the next release).

Every ‘requirement’ may be embodied in one or more GitHub issues, as a single requirement, i.e. feature, bug, improvement, may impact several GitHub repos.

Coordinating the resolution of a single ‘requirement’  across multiple GitHub repos adds complexity to our efforts, but this document proposes mechanisms to manage the complexity.

## Managing a Release

### Issues

A requirement is proposed as a GitHub issue or discussion in one of the openapi, RI, [Test Tool][test-tool] or [Specification][spec] repos. The creator of an issue must attempt to add the following to an issue:

- A clear problem statement independent of proposed solutions. This should typically take the form of a User Story "As a {role} I would like to {perform some function} so that {some business utility}". 

- An assigned owner

- Appropriate labels. (labels are found on the right in GitHub)

- Links to associated issues in other repos. I.e. an issue in the openapi repo almost always will require issues in the RI and Test Tool repos. It is the responsibility of the creator of an issue to create associated issues and link them together via URLs in the issue description.

A discussion within the profile WG will help the creator fill in information, perhaps the release target, that they may not know when the issue is created. The profile WG will periodically review all open issues and if the problem statement and solution are non-controversial, assign them a release target. 

To be sensitive to the cognitive overload of keeping up with emails from GitHub on every comment to an issue or PR, do not hesitate to pose questions or float ideas to individuals over email before resorting to GitHub.

### Pull Requests

A creator of an issue is encouraged to propose a solution.

Create an issue and review it with profile WG and make sure all relevant information is defined, especially links to issues in other affected repos.

From the issue page on GitHub, select ‘create a branch’

From the dialog box, select ‘Create a Branch’ (‘checkout locally’ radio button selected). Copy cmds from dialog box and paste them into your terminal window. Your environment will now be on the new branch.

Make your edits, commit them and push the results, i.e.

Test your changes locally.

```sh
git commit -a -m "made these edits"
git push
```

You may iterate on the above some number of times. Feel free to solicit feedback from others.

#### Create a Pull Request (PR)

Assign at least one reviewer

Repeat process for all affected repos.

Reviewer(s) will approve PR(s).

Merge PR(s)

Don’t forget to sync your local environment:

```sh
git checkout main
git pull
```

## Caveats

There are some extra steps for some circumstances.

### Updating tables in `Definition.md`

The `Definition.md` file contains some tables which are autogenerated from `openadr3.yaml`.

This update is handled by running `scripts/process.mjs` as discussed in [the README](scripts/README.md).

This task requires a setup step

* Installing Node.js v24 or later
* Running `npm install`

After that, with your terminal in the `scripts` directory, run:

```shell
$ npm run doit
```

### Generating PDF versions of the specification documents

The files `Definition.md` and `User_Guide.md` can be rendered to high-quality PDF documents using a script in the `scripts` directory.  This results in `Definition.pdf` and `User_Guide.pdf` files in the same directory.

This task requires a setup step

* Installing Node.js v24 or later
* Running `npm install`

After that, with your terminal in the `scripts` directory, run:

```shell
$ npm run dopdf
```

For details about how this works, see [README PDF](./scripts/README-PDF.md).

### Specification

Releases of openapi document live within separate files in [the specification repo][spec], e.g. `3.0.1/openadr3.yaml`, `3.1.0/openadr3.yaml`, etc.
Before editing a file for a given target release, make sure there is an existing file with the proper name, or create one. For example, if there is an issue in the repo describing a change targeted for release `x.y.z`, there must be a file named `x.y.z/openadr3.yaml`. When this file is created, the `info.version` string in the document must reflect the release and the filename.

## Publishing a Release

Once a set of PRs have been merged corresponding with a release target, we may ‘publish’ a release. Each repo will receive a new label marking the most recent commit as the released version.

Open and new issues must refer to the ‘next’ release (unless it is a micro-patch, a change to a previous release)

An announcement may be made by the Alliance

Subsequent certifications will be to the labeled release
